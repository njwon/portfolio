[기초] 웹 기초 부수기 및 웹 보안의 필요성!

기초웹통신

우리가 흔히 웹 사이트 혹은 웹이라 부르는 것의 정체는 무엇일까?
흔히 쉽게 지나쳐가는 웹 기초 다지기.

웹🕸️

HTTP 통신을 이용하여 정보를 공유하는 서비스.

우리가 웹사이트에 접속하면 HTML, CSS, JS와 같은 static한 리소스들을 불러온다.
이때, 정보를 제공하는 주체를 서버(Server) 정보를 받는 이용자를 **클라이언트(Client)**라고
부른다.
우리가 식당에 갈 때 음식을 서빙하는 사람(Server)과 음식을 주문받는 고객(Client)의 관계를 생각하면 편하다.

서버와 클라이언트의 관계

이렇게 보면 서버와 클라이언트의 관계가 명확히 딱딱 정해져 있는 것도 같지만, 그렇지만은 않다.

"클라이언트"와 "서버"는 고정된 직업이 아니라, 상황에 따른 역할이다.

서버가 클라이언트의 역할을 수행해 다른서버에 리소스를 요청할 때가 있다.
반대로 클라이언트 역할을 수행하던 내 컴퓨터에서 서버를 열수도 있다.
이와 같이 서버와 클라이언트는 고정돼있지 않으며, 상황에 따라 유동적으로 변화한다.
더 자세히 말하자면, 서버와 클라이언트의 관계는 **"누가 요청(Request)을 먼저 보냈느냐"**에 따라 상대적으로 결정된다.

웹 서비스와 보안

과거의 웹서비스는 처음에 서술한 static한 작업만 처리할 수 있었다.
HTML, CSS, JS, WebP.. 등의 리소스를 서빙만 할 수 있었다는 것이다.
현재는 과거의 웹 서비스와 달리, 이용자의 요청을 해석하고 가공하여 필요한 정보와 기능을 제공하는 능동형 서비스에 가까워졌다.
이러한 웹의 발전은 우리의 일상을 많은 부분에서 바꿔놓았으며, 오프라인에서 이뤄지던 많은 상호작용이 현재는 디지털 형태로 변환되어 웹 서비스로 구현되고 있다.
웹에서 처리하는 정보 자산들이 늘어남에 따라 이를 안전하게 보관하고 처리해야 할 필요성도 함께 증가하였다.
예를 들어, 고객이 물건을 구매한다고 가정해보자. 그 과정에서 고객의 주소, 카드 번호와 같은 정보들이 웹을 통해 서버로 전달된다. 만약 이 정보들이 안전하게 보호되지 않는다면 고객에게 심각한 피해를 야기할 것이다. 그래서 웹을 통한 정보의 교환 과정에서 이러한 민감한 정보들이 유출되거나 악용되지 않도록 보호하는 웹 보안의 중요성이 대두하고 있다.

API

API(Application Programming Interface)는 한마디로 프로그램끼리 대화할 수 있게 해주는 연결 통로다. 레스토랑 비유로 예시를 들어보겠다.
**손님(클라이언트)**은 배가 고파도 주방(서버)에 직접 들어가서 요리를 해먹을 수 없다. 대신 점원(API)에게 메뉴판(API 문서)을 보고 주문을 한다. 점원은 주문을 주방에 전달하고, 요리가 나오면 다시 손님에게 가져다준다. 손님은 주방이 어떻게 돌아가는지 몰라도 점원에게 말만 하면 원하는 것을 얻을 수 있다.

우리 주변의 예시로 보면 더 와닿는다. 날씨 앱이 직접 온도를 재지 않는다. 앱을 켜는 순간 기상청 서버의 API에게 "지금 서울 기온 알려줘"라고 요청을 보내고, 기상청 API가 "25도야"라고 응답하면 그걸 화면에 띄운다. "카카오로 시작하기" 버튼도 마찬가지다. 그 사이트는 내 비밀번호를 모른다. 카카오 서버의 API에게 "이 사람 카카오 회원 맞아?"라고 물어보고, 카카오가 인증 토큰을 돌려주면 로그인을 허용하는 것이다.

URI, URL, URN

웹에서 자원을 가리키는 방식에는 세 가지 개념이 있다. 관계부터 이해하면 쉽다. **URI(Uniform Resource Identifier)**는 가장 큰 개념으로, 자원을 식별하는 모든 방법을 통칭한다. **URL(Uniform Resource Locator)**과 **URN(Uniform Resource Name)**은 그 하위 개념으로, URI = URL + URN이 성립한다.
사람을 찾는 상황에 비유하면 이해하기 쉽다. URL은 "서울시 강남구 역삼동 123번지"처럼 위치를 알려주는 방식이다. URN은 "주민번호 900101-1234567"처럼 고유한 이름으로 식별하는 방식이다. 이 번호를 지도 앱에 쳐봤자 집이 나오지는 않는다.
사실상 99% URL을 의미하면서 URI라는 용어를 쓴다. REST API에서 "자원 식별자"라는 의미를 강조하기 위해 URI라고 많이 부르는 것이고, 일반 대화에서는 URL이라고 해도 전혀 문제없다.

웹 리소스

웹 리소스란, 웹에 갖춰진 정보 자산을 의미한다. 웹 브라우저의 주소창에 http://njw.kro.kr/index.html 주소를 입력해보자. 이는 njw.kro.kr에 존재하는 /index.html 경로의 리소스를 가져오라는 의미이다. 모든 웹 리소스는 고유의 **Uniform Resource Identifier (URI)**를 가지며, 이를 이용하여 식별된다. 웹의 프론트엔드를 구성하는 대표적인 웹 리소스들은 다음과 같다.

1. Hyper Text Markup Language (HTML)
웹 문서의 뼈와 살을 담당한다. 태그와 속성을 통한 구조화된 문서 작성을 지원한다.

2. Cascading Style Sheets (CSS)
웹 문서의 생김새를 지정한다. 웹 리소스들의 시각화 방법을 기재한 스타일 시트이다. 글자의 색깔이나 모양, 배경 색상, 이미지의 크기나 위치 등을 CSS로 지정할 수 있다. 브라우저는 이를 참고하여 웹 문서를 시각화한다.

3. JavaScript (JS)
웹 문서의 동작을 정의한다. 이용자가 버튼을 클릭했을 때, 어떻게 반응할지, 이용자가 데이터를 입력하면 어디로 전송할지 등을 JS로 구현할 수 있다. JS는 이용자의 브라우저에서 실행되는데, 클라이언트가 실행하는 코드라고 하여 Client-Side Script라고도 부른다.

4. 그 외
문서, 이미지, 동영상, 폰트 등

웹 클라이언트와 서버의 통신

이 글에서 서술한 내용을 토대로 웹 서비스의 통신 과정을 간략화하면 다음과 같다.

(클라이언트) 이용자가 브라우저에 URL을 입력하여 웹 서버에 접속한다.

(DNS) 브라우저는 DNS 서버를 통해 도메인 이름에 해당하는 실제 서버의 IP 주소를 알아낸다.

(클라이언트) 브라우저는 이용자의 요청을 해석하여 알아낸 IP 주소의 웹 서버에 HTTP(혹은 HTTPS) 형식으로 리소스를 요청한다.

(서버) HTTP(혹은 HTTPS)로 전달된 이용자의 요청을 해석한다.

(서버) 해석한 이용자의 요청에 따라 적절한 동작을 한다. 리소스를 요청하는 것이라면, 이를 탐색한다. 계좌 송금, 입금과 같은 복잡한 동작을 요구할 경우 내부적으로 필요한 연산을 처리한다. 필요하다면 데이터베이스(DB)에서 자료를 찾거나 로직을 수행한다.

(서버) 전달할 리소스를 HTTP(혹은 HTTPS) 형식으로 이용자에게 전달한다.

(클라이언트) 브라우저는 서버에게 응답받은 HTML, CSS, JS 등의 웹 리소스를 렌더링한다.
