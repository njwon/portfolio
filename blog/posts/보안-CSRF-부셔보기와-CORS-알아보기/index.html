CSRF

CSRF란, 인증된 사용자가 자신의 의지와 무관하게 공격자가 의도한 행동(비밀번호 변경, 송금, 삭제 등)을 웹 애플리케이션에서 수행하게 만드는 취약점

사용자의 신원 정보가 포함되어있는 쿠키(세션, JWT)는 일종의 서명과 같은 역할을 한다.
**CSRF(Cross Site Request Forgery, 교차 사이트 요청 위조)**는 이러한 권한이 주어진 사용자를 이용해 사용자를 속여 의도치 않은 요청에 동의하도록 만드는 공격이다.

이미지를 보자. 이미지에선 공격자가 Stored XSS 취약점을 이용해 CSRF 공격 스크립트가 포함된 게시물을 등록하고 이를 이용자가 볼 수 있도록 하고 있다. 이용자는 CSRF 스크립트가 포함된 게시물을 열람하여 스스로 웹 사이트에게 요청을 보내 공격자가 의도한대로 작업이 이루어지는 것을 알 수 있다.

방식

CSRF 공격에 성공하기 위해서는 공격자가 작성한 악성 스크립트를 이용자가 실행해야 한다. 이는 공격자가 이용자에게 메일을 보내거나 게시판에 글을 작성해 이용자가 이를 조회하도록 유도하는 방법이 있다. 심지어는 공격자가 직접 자신의 사이트를 만들어 그곳에서 악성 스크립트를 작성할 수도 있다. 여기서 말하는 악성 스크립트는 HTTP 요청을 보내는 코드를 뜻한다.

XSS와의 차이점?

XSS와 CSRF는 스크립트를 웹 페이지에 작성해 공격한다는 점에서 매우 유사하다. 두 취약점의 공통점과 차이점은 다음과 같다.

공통점

두 개의 취약점은 모두 클라이언트를 대상으로 하는 공격이며, 이용자가 악성 스크립트가 포함된 페이지에 접속하도록 유도해야 한다.

차이점

두 개의 취약점은 공격에 있어 서로 다른 목적을 가진다. XSS는 인증 정보인 세션 및 쿠키 탈취를 목적으로 하는 공격이며, 공격할 사이트의 오리진에서 스크립트를 실행시킨다.

CSRF는 이용자가 임의 페이지에 HTTP 요청을 보내는 것을 목적으로 하는 공격이다. 또한, 공격자는 악성 스크립트가 포함된 페이지에 접근한 이용자의 권한으로 웹 서비스의 임의 기능을 실행할 수 있다.

CORS란?

CSRF 공격의 목적은 요청을 실행시키는 것 자체이다. 공격자는 응답을 굳이 읽지 않아도 된다. <form> 태그를 이용한 POST 요청이나 <img> 태그를 이용한 GET 요청처럼 단순한 방식으로도 송금이나 설정 변경은 충분히 가능하다.

하지만 여기서 공격자가 단순히 요청을 보내는 것을 넘어, 서버의 응답 데이터를 가로채거나(예: 계좌 잔액 조회, 개인정보 탈취), application/json 같은 커스텀 형식으로 정교한 요청을 보내려는 순간, 브라우저라는 문지기가 막는다. 바로 SOP 정책 때문이다.

흔히 CORS 에러라고 불리우는 에러 사진

여기서 SOP는 Same Origin인 서비스들끼리만 리소스를 공유할 수 있다고 했다.
그렇다면 <img> 태그들 같은 것들은 어떻게 작동할까? 분명히 Cross Origin인 리소스를 태그에 담을 수 있지 않은가. 사실 SOP는 Cross Origin끼리의 교환에서 모든 리소스를 막는 것이 아니다. 위에서 서술한 <img> 태그와 같은 이미지 말고도 <style>, <script> 등의 태그의 리소스 교환을 막지 않는다.
위 경우들 외에도 Cross Origin인 웹 서비스들끼리 데이터를 처리해야 하는 경우가 있다. 이때 자원을 공유하기 위해 사용하는 방법을 CORS라고 명칭한다.

CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 HTTP 헤더에 기반하여 Cross Origin 간에 리소스를 공유하는 방법이다.
발신측에서 CORS 헤더를 설정해 요청하면, 수신측에서 헤더를 구분해 정해진 규칙에 맞게 데이터를 가져갈 수 있도록 설정한다.
웹 리소스 요청 코드

/*
    XMLHttpRequest 객체를 생성합니다. 
    XMLHttpRequest는 웹 브라우저와 웹 서버 간에 데이터 전송을
    도와주는 객체 입니다. 이를 통해 HTTP 요청을 보낼 수 있습니다.
*/
xhr = new XMLHttpRequest();
/* https://theori.io/whoami 페이지에 POST 요청을 보내도록 합니다. */
xhr.open('POST', 'https://njwon.io/lol');
/* HTTP 요청을 보낼 때, 쿠키 정보도 함께 사용하도록 해줍니다. */
xhr.withCredentials = true;
/* HTTP Body를 JSON 형태로 보낼 것이라고 수신측에 알려줍니다. */
xhr.setRequestHeader('Content-Type', 'application/json');
/* xhr 객체를 통해 HTTP 요청을 실행합니다. */
xhr.send("{'data':'WhoAmI'}");

발신 측의 HTTP 요청

OPTIONS /lol HTTP/1.1
Host: njwon.io
Connection: keep-alive
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
Origin: https://bank.com
Accept: */*
Referer: https://bank.com/

위 요청 코드와 실제 요청된 HTTP 메세지를 보면 POST로 요청하도록 코드를 작성했지만 실제로는 OPTIONS 메서드로 메세지가 날라간 것을 알 수 있다.
이를 CORS preflight라고 하며, 수신측에 웹 리소스를 요청해도 되는지 질의하는 과정이다.

위처럼 질의하면 서버는 아래와 같이 응답한다.
서버 측의 HTTP 응답

    HTTP/1.1 200 OK
    Access-Control-Allow-Origin: https://dreamhack.io
    Access-Control-Allow-Methods: POST, GET, OPTIONS
    Access-Control-Allow-Credentials: true
    Access-Control-Allow-Headers: Content-Type

여기서 Access-Control-Allow-Origin은 요청을 처리할 수 있는 Origin을 의미한다.
Access-Control-Allow-Methods는 처리할 수 있는 메서드 목록을 뜻하고,
Access-Control-Allow-Credentials는 쿠키 사용 여부를 판단한다.
Access-Control-Allow-Headers는 헤더의 사용 가능 여부를 나타낸다.

그러니 사실 CORS 에러는 진짜 CORS 에러라기 보다는 SOP 정책을 위반한 요청을 보내 뜨는 에러라고 보는것이 합당하다.

wargame 풀이

csrf-1 워게임 문제를 풀이해 보았다.

#!/usr/bin/python3
from flask import Flask, request, render_template
from selenium import webdriver
import urllib
import os
from selenium.webdriver.chrome.service import Service
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.common.by import By

app = Flask(__name__)
app.secret_key = os.urandom(32)

try:
    FLAG = open("./flag.txt", "r").read()
except:
    FLAG = "[**FLAG**]"


def read_url(url, cookie={"name": "name", "value": "value"}):
    cookie.update({"domain": "127.0.0.1"})
    try:
        service = Service(executable_path="/usr/local/bin/chromedriver")
        options = webdriver.ChromeOptions()
        for arg in [
            "headless",
            "window-size=1920x1080",
            "disable-gpu",
            "no-sandbox",
            "disable-dev-shm-usage",
        ]:
            options.add_argument(arg)

        driver = webdriver.Chrome(service=service, options=options)
        driver.implicitly_wait(3)
        driver.set_page_load_timeout(3)
        driver.get("http://127.0.0.1:8000/")
        driver.add_cookie(cookie)
        driver.get(url)
    except Exception as e:
        print(str(e))
        driver.quit()
        # return str(e)
        return False
    driver.quit()
    return True


def check_csrf(param, cookie={"name": "name", "value": "value"}):
    url = f"http://127.0.0.1:8000/vuln?param={urllib.parse.quote(param)}"
    return read_url(url, cookie)


@app.route("/")
def index():
    return render_template("index.html")


@app.route("/vuln")
def vuln():
    param = request.args.get("param", "").lower()
    xss_filter = ["frame", "script", "on"]
    for _ in xss_filter:
        param = param.replace(_, "*")
    return param


@app.route("/flag", methods=["GET", "POST"])
def flag():
    if request.method == "GET":
        return render_template("flag.html")
    elif request.method == "POST":
        param = request.form.get("param", "")
        if not check_csrf(param):
            return '<script>alert("wrong??");history.go(-1);</script>'

        return '<script>alert("good");history.go(-1);</script>'


memo_text = ""


@app.route("/memo")
def memo():
    global memo_text
    text = request.args.get("memo", None)
    if text:
        memo_text += text
    return render_template("memo.html", memo=memo_text)


@app.route("/admin/notice_flag")
def admin_notice_flag():
    global memo_text
    if request.remote_addr != "127.0.0.1":
        return "Access Denied"
    if request.args.get("userid", "") != "admin":
        return "Access Denied 2"
    memo_text += f"[Notice] flag is {FLAG}\n"
    return "Ok"


app.run(host="0.0.0.0", port=8000)

xss-1와 마찬가지로 FLAG 변수에 플래그가 담기는 것을 알 수 있다.

/vuln 엔드포인트에서는 파라미터를 모두 소문자로 변환해 "frame", "script", "on" 이 세 키워드를 모두 "*"로 치환하고 반환해 XSS 공격이 불가능하다는 것을 확인할 수 있다.

이 부분에서 /flag 엔드포인트에 POST 메서드로 요청이 오면 check_csrf에 사용자의 요청값과 플래그를 포함해 넘긴다.

check_csrf는 동적으로 URL을 만들어 서버에서 chrome 드라이버를 통해 127.0.0.1 자기 자신을 의미하는 루프백 주소에 쿠키를 만들고 동적으로 만든 URL을 열어본다는 것을 알 수 있다.

/memo 엔드포인트를 살펴보면 render_template()을 이용해 입력값을 출력하기 때문에 XSS가 발생하지 않는다는 것을 알 수 있는데 전역 변수 memo_txt에 파라미터 값을 지속적으로 기록하고 출력하는 것을 알 수 있다.

/admin/notice_flag 엔드포인트는 접속 호스트의 주소가 루프백 주소이며 파라미터가 admin이어야지만 플래그를 memo_txt에 추가한다.

취약점 분석

/admin/notice_flag 엔드포인트를 이용하면 플래그를 획득할 수 있어보인다.
하지만 반드시 루프백 주소로 admin 파라미터로 접근해야지만 플래그를 보여주고, 서버 또한 쿠키를 루프백 주소에 저장하므로 <img src="/admin/notice_flag?userid=admin">와 같은 "frame", "script", "on" 키워드를 사용하지 않는 CSRF 페이로드를 /flag 엔드포인트를 이용해 동적으로 URL을 만들어 서버의 브라우저를 이용해 열어야 한다.

CSRF 방어

방어하기 위해서 쓰이는 가장 대표적인 것은 CSRF Token이다.
CSRF Token은 서버가 세션에 랜덤 토큰을 생성해서 심어주고 HTML의 <body> 안에도 담고, 이를 매 요청 시 비교하여 검증하는 식으로 동작한다.
공격자가 자신의 사이트에서 스크립트를 작성해 요청해도 토큰이 없기 때문에 막히고, SOP 때문에 공격자가 피해자의 페이지를 읽을 수 없어서 토큰값을 알아낼 방법이 없게 된다.
Referer / Origin 헤더를 검증하는 것과 SameSite일때만 Cookie를 보내도록 설정하는 것 또한 방어를 위한 방법으로 적합하다.

마무리

CSRF에 대해 공부해보았다. CSRF Token을 사용해 보았지만 정확히 원리를 파악하기 힘들어 헤맸던 경험이 있는데 블로그를 작성하며 조금 정리된 것 같다.
